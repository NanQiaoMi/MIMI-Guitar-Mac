# 真实曲库与本地启动连接恢复计划

日期：2026-10-20（用户时区Asia/Shanghai）。基线 `master@453b0d85`，实施 `fix/catalog-runtime-connection`。

## 已确认的原因

用户在4336看到演示数据/曲库暂不可用。health200，readiness503且数据库/目录不可用，已复制的音源3/3 ready。上轮稳定预览由主代理显式使用隔离不可达测试连接启动；本轮启动Docker Desktop后，GUI/backend进程存在，但引擎API有界探针超时，`docker-desktop` WSL发行版仍停止、5433无监听。`docker desktop start` 的“already running”不能证明数据库引擎就绪。这属于运行连接与数据库状态问题，不能通过去掉演示标记解决。

## 目标与保护边界

- 恢复已有本机真实曲库，分别证明进程存活、数据库可达、schema/迁移、真实目录读及原谱取回；不能以演示数据、空新库或媒体文件数量冒充恢复。
- 保留原 `D:\MIMIguitarweb` 分支和402行Git状态；本轮重新建立1025个普通文件的SHA-256基线，并已核对零变化。此前任务的1023文件清单位于已消失的临时目录，不能将两次快照之间的文件数量变化算成本轮修改。仅在隔离树改代码/构建，不读或输出.env、密码或令牌。
- 优先启动现有Docker与已存在数据库容器/卷，只读盘点数据和schema；不删除/重建容器卷，不导入覆盖现有数据、不seed演示曲库、不连接远程数据库。
- 若现有库缺schema，先给出当前版本依赖与数据保留方案。仅可在完整备份及可验证回滚保障下做必要且明确的本机增量迁移；不得drop/reset或强制将迁移标为已完成。数据源/目标不唯一时暂停依赖步骤并请求精确选择。

## 分工与实施顺序

1. 两名既有gpt-6-luna/max代理只读审查：Astro/Prisma standalone启动连接语义与测试连接混入；真实目录的表/字段/迁移依赖与只读验证。额度失败由主代理接手，不假定审查完成。
2. 主代理启动已安装的Docker Desktop后台进程，等待有界健康检查；读取既有容器状态、端口及卷身份，确认唯一项目数据库后只启动该容器。不创建空库当作修复，不触碰无关容器。
3. 本机数据库只读核验：当前库名、Tab/Article等计数、字段集合、迁移记录和代表性原谱引用。凭据仅在进程内传递，工具输出只包含脱敏状态和数量。
4. 恢复4336真实本机连接，验证目录API返回真实source、搜索/详情与原谱一致。若现有数据库无法恢复，保留诚实降级并明确具体阻碍，不把备份推断成已恢复。
5. 根据审查实现最小可重复的本地启动/诊断工具，明确区分日常真实曲库启动和测试/演示启动；保留个人练习在数据库不可用时的可用性，不在普通start中自动迁移/创建库、读取远程凭据或扫描全媒体。
6. 行为测试覆盖目标身份/状态、环境优先级、测试连接误用与凭据脱敏、失败退出与已有库保护；之后 `npm test` → `npm run build` → `npm run typecheck`，必要时独立只读数据库集成核验。任何新增失败不得合并。
7. 本地no-ff合入干净master并再次回归，启动4336，实际浏览器验证真实曲库来源、搜索、吉他/尤克里里详情和原谱。更新DEV_LOG、证据和限制，复核原目录保护，清理本轮临时标签/服务；不推送/部署或建立远程连接。

## 已确定的启动入口

- 保留 `npm start` 的独立启动行为，让个人导入与练习在数据库断开时仍可用。新增 `npm run start:local` 与只读的 `npm run start:local -- --check`，作为已有本机真实曲库的明确入口。
- 仅检查唯一名称 `mimi-guitar-pg` 的既有PostgreSQL容器、持久卷及主机端口；客户端连接固定为127.0.0.1。不更改现有主机端口绑定，不创建、启停、重建或恢复数据库容器。
- 有界执行Docker命令，以只读事务核验现有库、非空业务数据、当前schema与迁移。既有 `DATABASE_URL` 与确认的容器目标不一致时退出，不能静默覆盖、连接测试库或远程库。
- 凭据只在子进程内传递，不写文件，不输出原始Docker配置、连接串或数据库错误。启动检查不能替代 `/api/readiness` 的资源抽样或真实设备验收。
- Docker授权、登录或系统提示必须由用户处理；若引擎无法恢复，独立完成工具、测试和文档，保持真实曲库恢复一项未完成。

## 恢复中的结构核验与记录对齐

Docker引擎恢复后，只启动了创建于2026-09-28的既有 `mimi-guitar-pg` 容器和 `mimiguitarweb_pgdata` 卷。只读事务确认原库有16233条Tab、8条Article；前三条迁移完成，最后一条没有记录。最后迁移要求的 `scoreUrl` 可空、`format` 为text/非空/默认gp、`xheUrl` 为可空text已经全部存在。直接重放这条含ADD COLUMN的SQL会发生重名错误。

后续仅在以下证据全部成立后，按 [Prisma 6已有补丁的迁移历史对齐流程](https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/patching-and-hotfixing) 登记已存在的结构：

1. 生成本轮新的完整custom-format数据库备份，文件仅保留在用户私有任务证据目录；记录SHA-256并用pg_restore解析全部归档内容到/dev/null，不恢复到真实库。
2. 使用Prisma 6的只读schema diff，确认实际库与当前schema整体无差异；再次确认最后迁移无记录、前三条完成。
3. 对五张业务表生成只读行数和内容摘要，作为前后保留证明。仅执行 `prisma migrate resolve --applied 20261015000000_tab_score_resources` 对齐迁移元数据，不执行迁移SQL、不改字段、不改曲谱或账号数据。
4. 比较业务摘要与备份指纹，核对新增的迁移记录及当前readiness。若任一前提不满足，停止该步骤；不能仅凭字段名称或为消除提示强制登记。

这是一项有备份、可审计的既有结构登记，不作为日常启动入口的自动行为。未进行真实库恢复演练时要明确注明；元数据回退可精确定位本轮新增记录，不需要覆盖业务表。
